# 備份與還原計畫（上線前草案）

狀態：規劃文件，尚未配置供應商備份、排程或實際還原。CSV 匯出不是完整備份，也不能還原訂單關聯、圖片檔、稽核紀錄、權限及資料庫設定。

## 目標與原則

- 上線前先確定可接受的資料遺失時間（RPO）、可接受的復原時間（RTO）及保留天數；初始目標建議至少保留 30 天可用備份，但須先確認所選方案實際支援。
- 備份需涵蓋資料庫、商品圖片／儲存物件、必要設定及 schema/migration 版本；秘密金鑰以獨立的安全方式保存，不放入程式碼或一般 CSV。
- 至少保留一份與主要服務帳戶／儲存位置隔離的副本；限制存取並避免把客戶聯絡方式、成本、供應商資訊放進不必要的匯出檔。
- 免費方案可能沒有自動備份、時間點還原或足夠保留期。必須核實目前方案、配額、暫停規則、匯出限制與還原成本，不可只依宣傳頁推定。
- 任何正式還原都要先停止或凍結寫入、保存事故前快照、指定操作者、記錄時間與原因；先還原至隔離環境驗證，再核准切換。

## 備份範圍

1. PostgreSQL schema、資料表資料、必要函式／trigger／policy／索引及 migration 版本。
2. 商品圖片及其他使用中的 Storage 物件，包含路徑與 metadata。
3. 商品、分類、圖片排序、庫存餘額及異動、採購批次、訂單與訂單項目、費用、稽核紀錄、應用程式設定。
4. 版本化程式碼、部署設定清單與非秘密環境設定名稱。
5. 重要供應商／平台設定的復原說明；不要把 API token 或密碼寫入備份文件。

## 建議執行頻率（需依供應商功能驗證）

- 自動備份：若供應商方案支援，至少每日一次；重要資料變更前另外建立受控快照。
- 圖片：依儲存服務能力做版本化或定期複製，並驗證檔案數量、大小與校驗值。
- 匯出補充：管理員可定期匯出商品、庫存異動、採購、訂單、費用及稽核資料；匯出應標示產生時間、schema 版本與資料範圍，並安全保存。
- 還原演練：初期每次正式上線前至少一次，之後至少每季一次或在重大架構變更後一次。

## 還原流程

1. 建立事故紀錄：影響範圍、發現時間、最後確認正常時間及決策者。
2. 暫停受影響寫入或切換唯讀，避免還原期間出現新舊資料混寫。
3. 保留事故後現況與可用快照，不覆蓋唯一副本。
4. 還原到隔離 staging，依正確 migration 版本還原 schema、資料、Storage 物件與必要設定。
5. 驗證關聯完整性、商品數、圖片可讀取率、訂單／訂單項目、庫存餘額與 movement 加總、稽核紀錄、權限與 RLS。
6. 使用匿名角色與一般登入角色確認無法讀取成本、精確庫存、供應商、客戶及財務欄位。
7. 由負責人核准後安排切換；記錄資料時間點、缺失、操作者與結果。若驗證失敗，保留原系統並停止切換。

## 上線前必須確認

- [ ] 供應商與方案確實支援的自動備份頻率、保留期及還原方式。
- [ ] 資料庫和 Storage 圖片都有可操作的備份。
- [ ] 備份副本的權限、加密、保存位置及刪除期限已確認。
- [ ] 已實際完成一次 staging 還原，不只是看到備份檔存在。
- [ ] 還原後通過庫存、訂單、圖片、權限、RLS 與公開欄位驗收。
- [ ] 已定義正式事故時誰能批准還原與切換。
- [ ] 明確告知管理員 CSV 不是完整備份，也不能直接覆蓋正式資料。
