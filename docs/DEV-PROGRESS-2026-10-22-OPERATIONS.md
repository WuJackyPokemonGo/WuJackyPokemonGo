# 2026-10-22 接續：採購與訂單管理

使用者回覆已試過上一版並要求繼續。此為使用者自行回報「試過」，不等同全部手機驗收項目逐項通過。

## 本輪完成

- 後台切換商品／採購／訂單管理。
- 採購輸入商品、實際日期、數量、單位成本、其他費用、供應商、來源參考和內部備註；新增採購不加庫存，確認實際到貨才透過既有原子 RPC 入庫。
- 新增及編輯未確認／未收款訂單，多品項、售價與成本快照、平台費、其他成本、客戶代稱、管道及私有聯絡資料。整筆與品項在同一交易儲存；後續商品改名不影響歷史品項。
- 訂單合法狀態轉換。確認訂單前需補齊售價與成本；標記已收款前需輸入全額實收、實際收款時間及參考。只有管理員記錄已發生的外部交易，不會轉帳／付款。
- 訂購參考、實際退款金額／時間／參考。退款不增加庫存，實際商品退回可再販售時另做回庫；回庫不改退款金額。
- 完成交付使用已驗收的既有原子扣庫存 RPC；不允許負庫存。
- 每個新業務操作皆保存伺服器端 request ID 與結果，重送同一請求不重複新增／入庫／扣庫存。登入者的待確認請求以 sessionStorage 保存；發生不明網路結果後，即使後續重試收到登入拒絕，也保留原 key，待重新登入重試。
- 未完成的金額／日期由表單明確要求，不猜測。售價或成本未明時允許先存待確認訂單。
- 訂單搜尋、狀態篩選、處理紀錄；列表使用 API 分頁讀取，超過 20,000 筆明確報錯。
- 修正上一版 catalog RPC 使用 SQLSTATE 40001 表達編輯衝突的問題，改為 PT409。官方文件說明 PostgREST 14 可能對 40001 重試。前端及回歸驗收已同步。

## SQL 與權限

`supabase/staging/order-purchase-management.sql`、`catalog-conflict-response.sql` 透過 execute_sql 套用於 `wlrwlqchlxehlvkyesnj`，沒有新增 migration history。原來 schema 檔與本輪 schema 檔不可重跑。

業務實作位於 private，公開 facade 是 SECURITY INVOKER；每次驗證 auth.uid() 與可信管理員表，不使用可修改的 user_metadata。新 private.store_operation_requests 啟用 RLS、明確拒絕直接 client policy、撤銷 client grants，僅受控 RPC 可操作。原本訂單／採購／庫存直接寫入限制維持。

## 驗證

- Node 85 項測試通過，正式 bundle 建置通過。
- 真實 PostgreSQL 新驗收：匿名／非管理員拒絕，採購與訂單重送，收貨僅一次，無效品項整筆回滾，過期版本拒絕，不合法跳轉拒絕，未全額收款不能標記已付款，已付款不能改品項，完成扣庫存，改名不動快照，超額退款拒絕，退款與回庫分離，庫存帳實相符。
- 原商品分類／圖片核准驗收、舊庫存／採購到貨／完成／退回驗收再次通過，全部用 BEGIN/ROLLBACK。
- 驗收後採購 0、訂單 0、operation requests 0、原商品 1，沒有留下驗收資料。
- 真實匿名 Data API 呼叫新 RPC 被拒絕（42501）。
- 瀏覽器使用完全離線的 SDK fixture 檢查商品啟動、採購清單／表單、訂單清單／詳情、收款狀態欄位及取消狀態隱藏收款欄位。這不代表已用擁有人帳號實測新流程，也沒有進行真正付款／退款。QA fixture 不會放入部署目錄。
- Security advisors 僅剩既存 Auth leaked-password protection disabled 警告；未改方案或 Auth 設定。

## 範圍與接續
