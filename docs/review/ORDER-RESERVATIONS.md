## 訂單在哪一步正式成立

| 入口 | 建立時狀態 | 正式成立（開始保留） |
|---|---|---|
| LINE／Threads 等手動訂單（後台「新增訂單」） | 待審核 `pending_review` | 改為 **待付款** `awaiting_payment` 時 |

兩個入口共用同一個資料庫觸發器：訂單進入「待付款／已付款待採購／已向供應商訂購／到貨待確認」任一狀態就保留；待審核不保留。

## 保留規則
- 依訂單項目的商品，挑選狀態為「可出貨」的帳號（先入庫先出），改「已保留」並寫入訂單。已保留、已交付、待驗證、停用的帳號都不會被挑到。
- 現貨不足時保留能出的份數，缺口顯示為「待叫貨」（例：訂 3、有 2 → 保留 2、待叫貨 1）。補貨後按「補保留待叫貨訂單」依成立順序補上。
- 兩張訂單同時搶最後一份：挑選時用 `FOR UPDATE SKIP LOCKED`，只有一張拿到，另一張是待叫貨。
- 重送同一張訂單、狀態來回、重複按鈕：以「此訂單項目已綁定的帳號數」補差額，不會多保留。
- 訂單數量減少：釋放多出的已保留帳號。刪除品項：釋放該品項的帳號。
- 取消（或交付前退款）：只釋放此訂單「已保留」的帳號，已交付的不動。
- 完成交付：沿用原本的「完成交付並扣庫存」（扣一次庫存帳），同時把帳號改「已交付」。帳號改已交付**不再扣庫存**，不會重複扣。
- 使用帳號管理的商品，若仍有待叫貨，不能按完成交付（避免把別張訂單保留的帳號交出去）。
- 公開結帳沿用目前的庫存限制，未更動。

## 試算表同步
- 寫入者只有網站後台；保留結果先存資料庫，再排入同步佇列。試算表暫時失敗時，保留照樣有效，後台顯示「待同步／失敗」並可按「重試失敗項目」。
- 每個帳號每次變更是一個版本；同一帳號有新版本時，舊的未寫入版本會作廢，只寫最新結果；寫入是覆寫儲存格，重試不會產生重複列。
- **只讀**「帳號明細」的標題列、帳號編號、商品編號、狀態欄；**只寫**狀態、訂單編號兩欄。帳密欄位不讀不寫，也不進資料庫。
- 狀態對照：可出貨 ↔ available、已保留 ↔ reserved、已交付 ↔ delivered、待驗證 ↔ verifying、停用 ↔ unavailable。
- 「從試算表更新帳號」：新帳號匯入；試算表上手動改成待驗證／可出貨／停用會同步；資料庫中已保留／已交付的帳號不會被試算表覆蓋；試算表上自己標「已保留／已交付」但網站沒有對應訂單的新帳號，先列「待驗證」。
- 庫存帳對齊：帳號管理的商品，庫存＝可出貨＋已保留＋待驗證的帳號數（第一次匯入會對齊，不與既有期初庫存累加）。

真實 PostgreSQL 併發（PGlite 為單一連線，無法驗證同時搶貨）：
```

```

## 需要設定的項目（上線前）
1. **商品編號**：目前 84 件商品的 SKU 全部空白。請把每件商品的 SKU 填成試算表「帳號明細」的商品編號，否則帳號無法對應商品（後台會列出「找不到商品編號」）。
2. **試算表欄位名稱**：預設標題為「帳號編號／商品編號／狀態／訂單編號」，分頁名稱「帳號明細」。若實際不同，請 GPT 提供，設在 `SHEET_SYNC_CONFIG`。
3. **Google 服務帳號**：在 Google Cloud 建立服務帳號與 JSON 金鑰，把試算表分享給服務帳號的 email（編輯者）。
4. **Edge Function secrets**（不放 GitHub）：`GOOGLE_SERVICE_ACCOUNT_JSON`、`SHEET_SPREADSHEET_ID`、選填 `SHEET_SYNC_CONFIG`、`SHEET_SYNC_CRON_SECRET`、`SHEET_SYNC_ALLOWED_ORIGINS`。
5. 套用 `supabase/review/order-reservations.sql`（正式專案一次）、部署 `supabase/functions/sheet-sync`。
6. 第一次在後台按「從試算表更新帳號」，核對匯入報告；之後每次保留／取消／交付自動排入同步，按「同步到試算表」或設定排程推送。
