# Threads 客人特徵與經營篩選：第一段（審核分支）

分支：`feature/crm-features-phase1`。**尚未套用到正式站。**正式站要等驗收通過、老闆同意後才套用。

## 前提
- 正式站目前有 **0 筆網站訂單**。過去的成交都在 Threads 私訊裡完成。
- 「熟客」「成交額」由「已接受的歷史成交」加上「已完成的網站訂單」計算。
- 網站訂單用 `orders.customer_alias` 等於客人名單名稱來對應。
- 歷史成交另存在 `crm_deals`，不寫進 `orders`，以免動到庫存、營收和訂單流程。

## 第一段做了什麼

| 功能 | 規則 |

| 手機卡片 | 顯示暱稱、聯絡管道、成交次數與累計、成交待確認筆數、等貨或關注的商品、下一步，以及另外還有幾件進行中 |

## 聊天怎麼判斷（全部只是建議）
- **交付**：店主訊息裡有「密碼」。
- **付款**：店主給匯款資訊後 3 天內，客人回「已匯／轉了」或傳圖片。
  - 這類只會標成「待核款」，不會自動變成成交。
- **案件怎麼分段**：
  - 交付後，客人再傳訊息就開新的一段。
  - 隔 14 天以上，而且上一則是店主，也開新的一段。
  - 已付款還沒交付時，客人改問別的商品，也另開一段。
  - 分批交付：3 天內、沒有新的付款，就併回原本那筆。
- **金額優先順序**：
  1. 客人付款訊息裡寫的金額。
  2. 客人出價、店主同意的金額。
  3. 店主付款前最後一次報價。
     - 報「一隻 N」而且買多隻，就乘以隻數。
     - 報「共、＝、一套」就當成總價。
  - 日期、天數、銀行代碼、8591 都會排除。
- **案件狀態**（由上往下，第一個符合的就是）：
  1. 已交付：已成交。
  2. 已付款：待核款。
  3. 客人最後在問價、問庫存或說要買：我欠回覆。
  4. 店主說有貨通知或已登記：等貨。
  5. 已給匯款資訊：7 天內是待付款，超過 7 天是棄單。
  6. 店主報了價、客人沒回：7 天內是已報價待回覆，超過 7 天是報價後客人未回（不算棄單）。
- **重新匯入**：
  - 不會產生重複，以 source_key 判斷是不是同一筆。
  - 人工改過的案件狀態會保留，新的系統判斷另外記在 `suggested_status`。
  - 已接受或已略過的成交不會被更動。
  - 等貨只會新增，不會覆蓋。
- **範圍**：第一輪只替 A 層（疑似付款或熟客候選，119 位）產生建議。

**已知限制**：
- 抽查發現，有的金額抓到的是另一個商品的報價，所以每筆成交都要老闆確認。
- 等貨只抓到 1 筆。老闆常用的說法（「有多的跟您說」）大多是當下回覆，不一定代表在等貨。等貨主要靠手動新增。
- 用遊戲內交換交付的成交（沒有帳密訊息）會停在「待核款」，要人工改成已成交。
- 隻數是從交付訊息估的，可能不準。
