# 訂單生命週期與庫存影響規格（草案）

狀態：規格草案，未實作資料庫交易函式，未連接正式資料。所有狀態變更都應由受權限保護的伺服器端操作完成，不能只由前端改文字。

## 狀態與允許轉換

| 目前狀態 | 可轉換至 | 操作要求 |
|---|---|---|
| `pending_review` 待確認 | `awaiting_payment`、`cancelled` | 人工確認供貨、最終價格、交付方式；詢價不等於成立訂單 |
| `awaiting_payment` 待付款 | `paid_awaiting_purchase`、`cancelled` | 收款金額與時間由管理員確認；未收款不能記成已收款 |
| `paid_awaiting_purchase` 已收款待叫貨 | `ordered_from_supplier`、`refund_pending` | 保存採購依據；取消需記錄原因並走退款處理 |
| `ordered_from_supplier` 訂購中 | `arrived_for_check`、`refund_pending` | 記錄供應商訂單／來源參考與預計到貨資訊 |
| `arrived_for_check` 已到貨待驗 | `completed`、`refund_pending` | 先驗貨；到貨驗收與庫存增加應是同一個交易式操作 |
| `completed` 已完成 | `refund_pending` | 不允許直接改寫歷史訂單；售後以退款／補償流程處理 |
| `refund_pending` 退款處理中 | `refunded`、原狀態（僅在取消退款流程有明確稽核時） | 記錄退款金額、日期、外部交易參考與處理者 |
| `cancelled` 已取消 | 無直接復活 | 若需重新處理，建立新訂單並關聯原訂單，不刪除舊紀錄 |
| `refunded` 已退款 | 無直接復活 | 後續更正使用補償紀錄，保留退款歷史 |

## 庫存規則

1. 前台詢價清單不扣庫存、不預留庫存，也不代表訂單成立。
2. 確認付款本身不應自動扣庫存；是否扣庫存須依實際履約政策定義。此專案建議在「確定銷售並由管理員記錄」的原子交易中扣庫存，並產生唯一 sale movement。
3. 到貨驗收需在同一資料庫交易中建立採購到貨紀錄、增加庫存、寫入 purchase_received movement 及 audit log；交易任何一步失敗，整筆回滾。
4. 取消／退款不代表一律把商品加回庫存。只有實物確實可重新販售且經管理員確認後，才建立 cancel_return movement；退款與實物回庫是兩個不同事實。
5. 每個會改變庫存的操作都需幂等鍵（例如外部操作 ID／request ID），同一請求重送不得重複扣庫存或重複增加庫存。
6. 同一訂單項目的商品名稱、售價、成本快照、數量及詢價旗標需保留建立訂單時的值；後續商品改名或調價不得改變歷史帳。
7. 庫存餘額必須等於已確認的期初數量加上所有有效 movement 的 quantity_delta；對帳不一致時先阻止相關操作並告警，不可靜默改寫歷史 movement。
8. 收款、退款、費用、商品收入與庫存 movement 是不同紀錄；不能只靠訂單狀態推算實際現金流或利潤。

## 金額與報表

- 詢價商品沒有確認單價前，不得把它計入已確認收入或已收款金額。
- `public_subtotal_twd` 是對外商品小計快照，不等於已收款金額。
- 淨利估算至少須分開商品收入、歷史成本快照、平台費、其他費用、退款與未收款訂單；未收款金額不能當作現金收入。
- 退款需保存原收款關聯與退款金額；部分退款要明確支援，不可只用布林值表示。
- 訂單、庫存、收款、退款及稽核資料不應由 CSV 直接覆寫。

## 上線前測試

- [ ] 非法狀態轉換被拒絕，且不更動任何資料。
- [ ] 同一狀態轉換請求重送不會重複扣／加庫存或重複收退款。
- [ ] 到貨驗收任何一步失敗時，採購、餘額、movement、audit log 全部回滾。
- [ ] 取消與退款不會自動增加庫存；只有實物回庫並核准才新增 movement。
- [ ] 商品後續改名／調價不影響既有訂單快照與成本。
- [ ] 並行銷售不能造成負庫存；重複請求不會重複扣庫存。
- [ ] 退款、未收款、部分收款與費用報表可對帳。
- [ ] 匿名及一般帳號不能讀寫訂單、收款、退款、成本與庫存。
- [ ] staging 交易測試、備份與還原演練全部通過後，才評估正式上線。
